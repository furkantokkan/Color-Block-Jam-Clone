# D-001: Level Editor reads are runtime-gated

- Relation: AC_FAILURE (AC-4, Expected 5)
- Dedupe key: v2/read-mode/editor-runtime-gated
- Found by: independent verifier 2, 2026-09-25 (evidence.md)
- Symptom: `LevelDatabaseJson.TryRead(json, out levels, out error)` (3-argument) applies `LevelReadMode.Runtime`. The Level Editor's `LevelDatabaseFile.cs:37` (Save pre-read, Reload, Restore), `LevelDatabaseInspector.cs:79` and the `LevelDatabase.LoadJson` editor callers therefore refuse any file that contains an effect or cell object. The first save of a Barrier level works; every later Reload or Save fails with "... barrier is not implemented in gameplay yet."
- Fix (contract clarification): the 3-argument `TryRead` and `LevelDatabase.LoadJson(json, out error)` read in Authoring mode. Only `LevelDatabase.LoadAsync`, the game's project-scope load from Addressables, reads in Runtime mode through an additive `LoadJson(json, LevelReadMode, out error)` overload. The docs and README claims are corrected to match.
- Status: VERIFIED by independent verifier 4, 2026-09-25 (evidence.md, "Verification 4"; `captures/verify4-editor-save-reload.txt`). Editor save, reload and two more saves succeed identically, while the Runtime read refuses "Level bar cell object o1 effect barrier is not implemented in gameplay yet." A follow-up review finding (the refused game load emptied the shared cache and broke the open Level Editor after Play Mode) is fixed: `LoadAsync` keeps the previous cache on refusal. The test `FailedProjectScopeLoadKeepsTheAuthoringCache` covers it; the contract was revised for that line.
- Verify: a scratch database with an Arrow and a Barrier saves, reloads and saves again through the editor paths (`LevelDatabaseFile`, `LevelDatabaseInspector.Describe`, `LevelDatabase.LoadJson`). `LevelDatabase.LoadAsync`, or a direct test of the Runtime path, refuses the same file with a message naming the effect.
