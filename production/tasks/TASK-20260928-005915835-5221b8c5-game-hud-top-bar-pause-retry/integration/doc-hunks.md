| In-game pause menu, HOME and Back routing (DEC-154) | Implements DEC-135 with the shared popup of DEC-136. Pause (Playing, the opening hold included), Android Back while Playing without targeting, or a background return shows `SettingsPopupView`/`SettingsPopupPresenter` with HOME inside `UI/Game/Overlays/GameOverlays.uxml`, drawn over the purchase popup with a 49 % black scrim; the Hub popup is unchanged. One plain C# owner, `GameMenuFlow`, shows one overlay at a time and talks to the session through the narrow `IGameSessionControl` port: Pause(User) first, then the menu; Close, the scrim or Back resume and are disabled while a booster write is pending. With a HUD the installer binds `PopupPauseOverlay` (`ResumesOnForeground` false) instead of `NoPauseOverlay`, retiring DEC-116's foreground auto-resume for the Game HUD; HUD-less scenes keep `NoPauseOverlay` and `UnavailablePurchaseHost`. `ApplicationPauseRelay` forwards to an optional `IApplicationPauseListener`, so a Paused(Saving) or Paused(Purchase) session latched to Background (no state notification) shows the menu on return and never resumes behind it; the purchase popup is hidden first so one Back press has one handler. Back while Playing stays with `DragInputRouter`: targeting cancel first, otherwise the `IGameplayBackFallback` set by the flow; while an overlay is open a code-built `<Keyboard>/escape` action closes it. HOME calls `GoHome()` and then `IHubSceneTransition` (default: `OnitySceneFlow.TransitionAsync(profile, Hub)`, no loading screen, DEC-140; in the Editor's Test Level it ends Play Mode, DEC-127), guarded once, cancelled if Game unloads mid-await; the menu stays up during the exit. Won/Failed have no result popup yet: Pause opens the menu without a session pause so HOME stays reachable. Task `TASK-20260928-005915835-5221b8c5-game-hud-top-bar-pause-retry`. |
