# Color Block Jam Case: Project Rules

Product and runtime rules for this project. `AGENTS.md` covers tooling and
packages. The case brief is `docs/Game-Developer-Case-2026.md`.

This is a mobile game for Android and iOS. Rabbyte Games branding is reserved
for PC games; its studio name, logo and opening intro are not used here
(owner clarification, 2026-09-30).

Evaluation order from the brief: architecture, editor usability, code quality,
correctness, performance, then scope control. When two options compete, choose
the one that ranks higher on that list.

## UI Authoring

- UI is authored for human editing: reusable UXML/USS documents open as visible,
  modular components with their common styles, fonts and representative content.
  Artists edit the real template, not a duplicated mockup or a runtime-generated
  hierarchy. Layout, sizing, spacing, typography, colors and static content stay
  in those assets. Runtime assigns only actual dynamic data and state.
- Open `Assets/ColorBlockJam/UI/Purchase/BoosterPurchasePopup.uxml` directly in
  UI Builder and use a 1080 x 1920 canvas. Expand `booster-purchase-safe-area`
  to edit the popup; select its `.booster-purchase-*` classes for shared styles.
  There is no preview visibility toggle to restore. Common.uss and the runtime
  font are loaded by the popup stylesheet. Its sample Rocket offer is for
  authoring only; both text layers must match when changing a sample label.
- Hub booster purchase, Hub life refill and Game purchase reuse that one
  template. Their named template instances start hidden through scoped host
  rules, so delayed/lazy binding cannot show or intercept input with a sample
  offer. Constructing `BoosterPurchaseView` also starts closed. Runtime
  `SetOffer` replaces every sample field; `SetVisible` controls opening/closing
  inline. Do not move layout construction into C# or replace authored samples
  with economy defaults. Other existing overlays are migrated only in their
  own scope after checking their initialization and re-enable behavior.

## Game States

The level session has one state at a time. The session state is the only
source of truth for "is the game running". Systems do not keep their own
game-over or paused flags.

| State | Gameplay runs | Entered from | Leaves to |
| --- | --- | --- | --- |
| `Home` | No | App start, Won, Failed, Paused | Playing |
| `Playing` | Yes | Home, Restart | Paused, Won, Failed |
| `Paused` | No, suspended | Playing | Playing, Restart, Home |
| `Won` | No; bounded visual Finish, then torn down | Playing | Next level (Playing), Home |
| `Failed` | No, torn down | Playing | Restart (Playing), Home |

Settings is an overlay on `Home`. It is not a session state.
The pre-level popup is also an overlay on `Home`: Level opens it, Play builds
the attempt while still on `Home`, and close/Back before Play returns to Home
without a spend. A zero-stock booster purchase popup during play uses `Paused` and the
existing Suspend/Resume path; it does not create another gameplay state.

For selected starting boosters, build and validate the board, warm pools,
resolve valid targets and commit their combined stock debit while on `Home`.
If backgrounded during this write, keep the prepared intent on Home and wait
for explicit Play; reuse its committed debit/target without spending or rolling
again. Closing after commit discards the intent without refund.
In the Game scene, which has no Play control, returning to the foreground is
that explicit Play (DEC-149).
Invalid selections spend nothing; a failed save starts no effect. Only then
enter `Playing`, dim the screen with one icon per starting booster, and once the
dim has faded apply the captured commands once in the next command phase, Extra
Time before Rocket (DEC-166). The session owns the opening presentation and
holds normal board/HUD booster input and countdown until it finishes. Pause
preserves its progress; Resume never reapplies an effect. Teardown cancels
the sequence and clears its selection. With no selection, play starts normally.
`Saving` is a pause reason, and `Finish` is a presentation operation; neither
adds a sixth session state (DEC-92, DEC-93).

## Scenes and Onity Scopes

- `Init` is the startup scene and the app's only loading screen (DEC-140).
  Onity loads the persistent `ProjectContext` before any scene, so direct Play
  in `Game` also has app-wide services. `Init` shows the loading bar from its
  first frame while that scope loads, builds `Hub` additively behind it, and
  unloads itself once Home is bound and the level Home offers is prepared
  behind it (DEC-199). It may later host server initialization and SDK or
  intro triggers; none are required now.
- `Hub` owns the Home screen: level selection, its tab group, Settings and
  pre-level selection. It has a `SceneContext`; choosing Play opens `Game`.
  The reference screen defines this ownership, but its visual UI is future
  work. Set Onity's Default Hub Scene Name to `Hub` and leave Default Main
  Menu Scene Name empty; there is no separate main-menu scene.
- `Game` owns the level attempt. Its `SceneContext` owns scene services and
  disposes them when the scene unloads. Level attempts remain shorter-lived
  and follow the session ownership rules below.
- No other transition shows a loading screen, level transitions included:
  `Hub`, `Game`, Restart and next level load or rebuild directly. The scene-flow
  profile names no Loading scene and the build has none (DEC-140). Every scene
  change (Init's handoff to Home, Play, next level and Home) runs behind a short
  black fade that hides the load and the new scene's build frames; Restart
  rebuilds in place without one (DEC-198). Play and Continue skip the fade when
  their level is already prepared: Hub builds the level it offers in a hidden
  `Game` scene behind Home, the win popup builds the next one behind itself,
  and the start swaps the scenes in one frame; the fade stays the fallback
  (DEC-199).
- `LevelEditor` is an authoring-only scene, independent of player navigation.
  Exclude it from player builds and prevent it from running in Play Mode.
  The Level Editor's Test Level plays the Game scene as the Play Mode start
  scene instead, and Unity reopens the LevelEditor scene afterwards (DEC-127).
  It does not create a player session or start the runtime scene flow.
  While it is loaded, an editor-only DontSave preview shows the level selected
  in the Level Editor window (DEC-102, [Level Editor Scene Preview](docs/Level-Editor-Scene-Preview.md)).

Every runtime scene supplies its own Onity `SceneContext`; scene services never
become app-wide by accident. App services live only in the `ProjectContext` and
are disposed when the application scope ends. Each runtime scene can enter
Play Mode directly for focused development (DEC-98).
The repeated `SceneScope` GameObject name is only a hierarchy label. Each
scene's `SceneContext` creates a separate child container, with
`ProjectContext.Instance` as its runtime parent even when the Inspector's
parent fields are unassigned.
Onity's `ProjectContextBootstrap` loads the prefab from
`Assets/ColorBlockJam/Resources/Onity/ProjectContext.prefab`. Our
`ProjectScopeInstaller` does not start that scope; it registers the shared
scene-flow profile inside it. Other projects need a custom project installer
only when they have app-wide bindings to register.

## Runtime Lifecycle: Nothing Runs Unattended

Every loop, timer, subscription, tween, async task, and input callback has one
owner and a defined stop point. Outside `Playing`, no domain gameplay runs.
The only terminal presentation exception is the bounded foreground `Won`
Finish described below, before the popup. Owned save-service work may run in
`Home`, `Paused`, or terminal states, outside the `Playing` tick.

Example: when the win or fail popup opens, the timer, block movement, gameplay
input, and gameplay tweens have already stopped. The popup never opens on top
of a game that is still running.

### Ownership

- One level session object owns the lifetime of each level attempt. It holds
  the state, a `CompositeDisposable`, and a `CancellationTokenSource`.
- Everything that gameplay starts during an attempt registers with the
  session: subscriptions, tasks, tweens, and pooled objects.
- Views own only their own presentation work. They stop it in `OnDisable`.
- The app-scoped save service owns and awaits persistent writes with its own
  lifetime token. An attempt ending cannot cancel or replay a committed write.
  Completion callbacks check the attempt/view generation before touching UI
  or resuming a session; no write is fire-and-forget.

### Suspend and Teardown

Leaving `Playing` always suspends gameplay or ends it. `Won` stops domain
gameplay immediately, may run Finish, then runs Teardown. `Failed` captures
the static result background and runs Teardown immediately. A result popup
opens only after Teardown; a pause popup opens only after Suspend.

**Suspend** (`Paused`, can resume):

1. Disable the gameplay input action map.
2. Pause the level countdown and any remaining Time Freeze duration.
3. Pause gameplay tweens with `Tween.SetPausedAll(true, target)`.

`Paused(Saving)` uses these same steps without opening the pause popup.
Clear drag/pointer commands, retain only the accepted immutable booster
intent, and return from the accepting tick immediately: no later timer or
gameplay phase runs in that tick. Backgrounding latches an ordinary pause,
so a late save completion cannot resume gameplay automatically.

**Teardown** (`Won`, `Failed`, `Home`, Restart, next level):

1. Disable the gameplay input action map.
2. Stop the level countdown and Time Freeze duration.
3. Stop gameplay tweens with `Tween.StopAll(target)`.
4. Cancel the session `CancellationTokenSource`.
5. Dispose the session `CompositeDisposable`.
6. Return pooled board objects to their pools.

**Won Finish** (DEC-93): latch `Won` once and immediately reject gameplay
commands, stop both clocks and domain ticks, and prepare the reward once.
The session may retain only the final exit, Vacuum, or Hammer presentation
for at most 0.8 foreground seconds. Finish advances visual transforms only;
callbacks cannot change occupancy, stock, rewards, or the terminal state.
Its owner and stop point remain the session, without another tick owner or
session state. Missing views, timeout, backgrounding, Home requests, or scene
unload force cleanup. Immediately before Teardown, capture a static board
image into a render target prewarmed at level load; if unavailable, use the
supplied background. The result popup dims this static image, with no live
board simulation or effects behind it. Failed uses the same capture without
Finish. Finish and Teardown never wait for a save; the popup can show pending
save or Retry feedback while navigation remains gated by the save policy.

### Rules

1. **One tick owner.** Gameplay MonoBehaviours do not declare their own
   `Update`, `FixedUpdate`, or `LateUpdate`. One owner ticks the gameplay
   systems, and only while the state is `Playing`.
2. **Terminal transitions happen once.** The first of `Won` or `Failed` wins.
   The session ignores later transition requests in the same attempt, for
   example when the last block exits in the frame the timer reaches zero.
3. **Every subscription is disposed.** Add each `Subscribe` result to the
   session `CompositeDisposable` or to its component with `AddTo(this)`. Never
   discard the returned `IDisposable`.
4. **Every async operation can be cancelled.** Do not use `async void`. Pass
   the owning session, component, or save-service `CancellationToken` to every
   `OnityTask` or `Task`.
   Do not fire and forget.
5. **Tweens can be found.** Gameplay tweens target gameplay objects, so
   `Tween.StopAll(target)` can stop them. UI tweens belong to the view that
   plays them.
6. **`Time.timeScale` is not the pause mechanism.** It does not stop input,
   async work, or unscaled code. The session state controls pause.
7. **Forbidden for gameplay:** `Invoke`, `InvokeRepeating`, coroutines, static
   events, and static mutable state.
8. **Restart leaves nothing behind.** Restart and Home tear down the attempt
   and rebuild it from `LevelData`. No value from the previous attempt
   survives. Persistent data, such as coins, booster stock and the current
   level, lives only in the save service. Restart preserves purchases and
   spent stock; it never refills or refunds boosters.
9. **Services clean up after themselves.** A service that starts work
   implements `IDisposable`. Its Onity context disposes it at its declared
   lifetime boundary: scene for board services, app for persistent saves.

### Verification

- EditMode tests on the session state machine prove that after `Won` or
  `Failed`:
  - a domain tick changes nothing,
  - the timer value stays the same,
  - gameplay commands are rejected,
  - a second terminal request is ignored.
- Finish tests prove final visuals complete or time out within 0.8 foreground
  seconds, forced cleanup works, and no callback changes domain state.
- Save tests cover commit/failure, duplicate callbacks, backgrounding during
  a write, stale attempt callbacks, and win-save Retry without double reward.
  Device fault-injection checks verify temporary-write/replace behavior and
  recovery of the last committed snapshot before claiming crash durability.
- A PlayMode or manual check after the finish popup, Home, and Restart shows:
  - `Tween.GetTweensCount(target)` is `0` for gameplay targets,
  - Onity `Onity/Tools/Task Tracker` shows no running task from the ended
    session,
  - Onity `Onity/Tools/Observable Tracker` shows no live subscription from
    the ended session (enable tracking in debug builds),
  - Onity `Onity/Tools/Pool Monitor` shows every board object returned to
    its pool,
  - the Profiler shows no gameplay script samples while the popup is open.
- Code review: each new `Update`, `Subscribe`, async method, tween, or loop
  must name its owner and its stop point.
- Device checks run on the team's Android phone connected over USB: the
  IL2CPP smoke build, frame rate and allocation checks with the Profiler
  attached, layout on the device's 20:9 screen, and the final full-flow test
  of the delivered APK. The Editor Game view with a 1080 x 1920 and a 20:9
  preset is the pre-check, not the final check.

## Architecture Rules

### Asset and Assembly Boundaries

- Place game-owned art, scenes, runtime code, and editor code under
  `Assets/ColorBlockJam`. Keep Unity `.meta` files with moved assets so their
  GUID references survive.
- The reusable `Haptics` library lives under `Assets/Haptics`, outside the
  game root. Its assembly has no game or Onity reference; the game-event and
  player-setting adapter remains in `Runtime/Haptics`. See [Haptics](docs/Haptics.md).
- Code lives in three roots, one folder per assembly (DEC-157):
  `Runtime/<Area>` for player assemblies (`Core` is `ColorBlockJam.Runtime`,
  then `Domain`, `Environment`, `Gameplay`, `Haptics`, `Hub`, `Player`, `Presentation`,
  `UI`), `Editor/<Area>` for Editor-only assemblies (`Core` is
  `ColorBlockJam.Editor`, then `Environment`, `LevelPreview`, `Validation`) and
  `Tests/<Area>/{EditMode,PlayMode}`. No runtime assembly sits under a folder
  named `Editor`. UI Toolkit UXML/USS/TSS live in the asset folder
  `UI/<Screen>` (`Common`, `Themes`, `Startup`, `Hub`, `Game`, `Settings`,
  `Purchase`), never beside scripts; editor-only icons and editor USS stay
  beside their editor code. Art, Data, Prefabs, Resources, Scenes and Settings
  hold no scripts. A new assembly gets its own `Runtime/`, `Editor/` or
  `Tests/` folder instead of nesting inside another assembly's folder.
- Keep project-authored ScriptableObject instances under
  `Assets/ColorBlockJam/Data`, grouped by feature. This includes booster
  databases and definitions and game-owned scene-flow configuration; the
  active level database needs no wrapper asset (DEC-194). Every authored JSON
  file lives under `Data/Json`,
  one subfolder per kind: level databases in `Data/Json/Levels`, one folder each
  (DEC-196), the piece library
  in `Data/Json/Pieces` (DEC-165, DEC-195). Engine and render-pipeline settings may stay
  under `Settings`.
- `ColorBlockJam.Runtime` in `Assets/ColorBlockJam/Runtime/Core` is the main game
  assembly and owns Onity composition and runtime services.
  `ColorBlockJam.Presentation` remains a separate view/effects assembly;
  presentation may depend on runtime contracts, but runtime code does not
  depend on presentation. `ColorBlockJam.Editor` stays Editor-only and may
  reference runtime contracts needed by authoring tools.
- Keep gameplay rules in plain C# with no MonoBehaviour. When their boundary
  is stable enough to justify a separate `ColorBlockJam.Domain` assembly,
  Domain must have no Unity or Onity references. Dependencies point from
  presentation, editor, and composition code toward stable domain contracts,
  never back outward; assembly references cannot form a cycle.
- Split another assembly only for a real, stable ownership or dependency
  boundary, not for each folder or feature. Test asmdefs use explicit
  references to the assemblies they verify and do not become player runtime
  dependencies (DEC-99).
- `ColorBlockJam.Domain` (`Assets/ColorBlockJam/Runtime/Domain`, no engine references)
  holds the board, move commands (DEC-122), movement, exit, picking and session rules;
  `ColorBlockJam.Gameplay` (`Assets/ColorBlockJam/Runtime/Gameplay`) holds the level
  session, the single tick owner, pointer input, the block presenter and the
  Game-scene installer, joining Runtime, Presentation and Environment the way
  `ColorBlockJam.Environment` does. `ColorBlockJam.Runtime` references
  neither (DEC-110, [Gameplay: Drag and Gate](docs/Gameplay-Drag-And-Gate.md)).

- Keep data, logic, and view separate. Board, blocks, doors, moves, and the
  timer are plain C# with no MonoBehaviour. Views are thin MonoBehaviours that
  render state and forward input.
- The level editor authors level databases under `Data/Json/Levels` directly. A
  database is a folder: `manifest.json` lists its level IDs in play order,
  grouped into `pack-NNN.json` files of at most 100 levels each, and together
  they are the sole source of its ordered `LevelData` records (DEC-196). Every
  manifest and pack belongs to the local `Level Database` Addressables group at a
  derived address with the `level-json` label. The editor dropdown chooses one
  active database for the game: the project scope installer on `ProjectContext.prefab`
  names its manifest through an Addressables reference (`LevelJsonReference`), and no
  ScriptableObject wraps it (DEC-194).
  Project scope reads only that manifest asynchronously into its own plain
  C# `LevelCatalog` before the Init route, and the Game scene loads the one pack
  its level needs on Home; the Level Editor keeps its own catalog with every
  level, so no two readers share parsed levels (DEC-192, DEC-196).
  The game copies selected values into an attempt-owned plain C# model; runtime
  play never mutates them.
  Designers use the editor rather than editing serialized files by hand.
  A block's `cells` are its only shape data: the game builds every block from
  them and never loads the piece library. A block type is its footprint key
  (`ShapeKey`, derived from the cells and never stored), so the same shape in any
  level, database or client is one piece (DEC-193,
  [Level data format](docs/Level-Data-Format.md#shape-identity-dec-193)).
- The persistent player save is a separate JSON snapshot. Level Create,
  Delete, and Save write the canonical level files after validation: only the
  packs whose text changed, then the manifest (DEC-196); Reload reads those
  same files. There is no level Import/Merge/Export workflow or
  second level authority. Save checks every file for prior external edits and
  retains one previous version of the whole database under
  `Library/ColorBlockJam/LevelBackups` for recovery.
- The per-frame path allocates nothing. Timer text updates only when the
  displayed second changes.
- Persistent coins, stock, current level and toggles form one versioned
  Newtonsoft JSON player snapshot behind a typed save service (DEC-92),
  replacing the pending PlayerPrefs design. Writes use a temporary file and
  atomic replacement; an unsuccessful commit keeps the previous snapshot.
  Serialize writes through one owner and publish reactive values only after
  commit. Level JSON loading, editor writes, and owned
  Home/Paused/terminal writes may allocate;
  serialization and file I/O never run in a `Playing` tick.
- For booster use, validate stock and target and capture a non-allocating,
  immutable command intent before entering `Paused(Saving)`. Persist the
  debit before mutating gameplay. A failed commit changes neither stock nor
  board and restores play unless backgrounding requires ordinary pause.
  Success applies that intent exactly once before the timer in the first
  resumed command phase. A backgrounded attempt requires explicit Resume;
  Home/Restart from that pause discards any committed pending intent without
  refund. Navigation and new submissions are gated while a write is pending.
  A kill after commit but before application keeps the charge spent: attempts
  are not recovered, refunded or replayed after relaunch. Home purchases stay
  Home, and in-game purchases use their already-Paused overlay.
- On Won, prepare +10 coins and progression as one intended snapshot once.
  A failed save exposes Retry of that same snapshot, never another addition.
  Continue and Home remain unavailable until commit; backgrounding preserves
  pending/failed save feedback on the result popup. T0 rewards and toggles
  use this same save owner. Editor test play uses an isolated in-memory store.
- Build the required scope first. Optional scope (validation, boosters, ice,
  arrow blocks) comes only after the required scope is complete.
- Layout targets 1080 x 1920 portrait and must stay correct on a 20:9 device.
- Board visuals are assembled from the modular kit, not modeled per shape.
  `BlockParts.fbx` supplies Center, Edge, InnerCorner and OuterCorner meshes;
  the imported kit contains no Base. Use only these original meshes. One gameplay
  cell spans two source half-cell tiles per axis (four LEGO studs). At each grid
  vertex, four occupied quadrants use four Centers, a straight boundary uses two
  Edges, a convex corner one OuterCorner and a concave corner one InnerCorner.
  Opposite quadrants use two convex corners. This replaces the unverified
  additive center/edge recipe, whose whole tops overlap.
  `WallAndDoor.fbx` supplies Wall, Corner_1, corner_3, corner_5, Door_1x1 and
  Door_Arrow; the rounded closed surface faces source -Y, so prefab children
  rotate X180 with their hidden underside at ground level. Do not use the
  defective corner_3.002. The project-authored wall and gate meshes are
  `Brick_End`, `Corner_End`, `Corner_Join` and `Door_End` in
  `Art/Models/BoardKit/WallBrick.fbx` (DEC-139), with their prefabs in
  `Prefabs/Board/Pieces/WallBrick/`, apart from the supplied files. They are
  built in Blender from the supplied Wall and door profiles inside Wall's,
  Corner_1's and Door_1x1's mesh bounds: `Brick_End` caps both ends of each
  straight outer-boundary wall run in the play area, `Corner_End` is an
  outer-boundary corner with a large quarter-round outer arc and both arm
  ends rounded, `Corner_Join` is that corner merged into its shorter wall
  beside a one-cell void, and `Door_End` closes both ends of each gate. The
  rule placements and the supplied meshes and prefabs are unchanged. `GroundGrid` spans one cell. `Arrows.fbx` supplies
  `Arrow_1`, `Arrow_2`, and `Arrow_3`, whole double-headed markers one, two,
  and three cells long. Their visual prefabs are centered, face local Z and sit
  just above the LEGO studs; horizontal placement uses a Y90 root rotation.
  The shared palette's Arrow Color is white by default. These are visual assets
  for later block Effect Data assignment. No automatic marker presenter or
  movement constraint is installed by the prefab preparation step. The planned
  effect selects the center-axis run and clamps longer runs to Arrow_3 without
  stretching, as specified in the mechanics catalog.
- The play-area environment (floor, walls, corners, doors, and the board
  camera framing of DEC-103) is a separate
  `ColorBlockJam.Environment` assembly (DEC-100, revised 2026-09-25). Wall and
  corner placement is authored in the project-owned rule set
  (`Data/Environment/EnvironmentRuleSet.asset`, UI Toolkit 3x3 Floor/Void/Any
  inspector) and evaluated by a plain C# matcher and composer over a half-cell
  quadrant grid with RuleTile's rotation semantics. The `Grid` on BoardRoot
  (cell 0.5, swizzle XZY) maps grid coordinates to local positions. No
  RuleTile, Tilemap or `com.unity.2d.tilemap.extras` package remains. All
  environment rules, piece prefabs and scales come from `Data/Environment/EnvironmentDatabase.asset`;
  the board layout contract (`IBoardLayout`) stays in `ColorBlockJam.Runtime`.
  See [Environment Layout](docs/Environment-Layout.md).
  Barrier board objects (OBJ-05) reuse the rule set on their own cells as raised,
  pooled wall pieces that sink below the floor when open; the gameplay owner moves
  them through `EnvironmentView.SetBarrierOpen`, whose session-owned tweens Suspend
  pauses and Teardown stops (DEC-121).
  Reusable tile prefabs are pooled. Every block root is the one bare prefab
  `Prefabs/Board/ModularBlock.prefab` with `BlockPiece`, bound as
  `BoardPieceCatalog.BlockRoot`; it shows the cells of the block it is checked out
  for (DEC-193, replacing DEC-120's derived per-shape prefabs).
  The piece library is editor-only. `Data/Json/Pieces/BlockShapeLibrary.json`
  (formatVersion 2, `{name, cells}` records, keys derived) holds the templates the
  Piece Editor saves, one per footprint key. It is the one fixed piece library,
  with no wrapper asset and no database choice (DEC-195): the Editor assembly's
  `BlockShapeLibrary` is an in-memory, never-saved object bound to that file, and
  no save writes an enum, a prefab or a script. Level-specific
  pieces never enter the library: they live as block cells with an optional
  per-level `pieces` name table (DEC-180, DEC-193). Every piece, templates included,
  holds at most 25 cells inside 5 x 5. Runtime `SetCells`/`TrySetCells` update
  copied attempt state and reuse the composer; one-cell removal rejects
  empty/disconnected survivors. Never mutate authored JSON or SOs during play. No
  new per-shape mesh is modeled.
- Ice is a shader, not new art. The single `icetexture.jpg` feeds one URP
  Shader Graph material that a frozen block shows as a second material on its
  own composed tiles; the shader expands each surface slightly outward, so no
  second object is spawned and a Rocket recompose keeps the ice (DEC-184).
  Frost tint, opacity, and a crack amount are shader parameters written into
  each tile's own `MaterialPropertyBlock`, the Ice pass reads the tile's clip
  plane, and the crack amount follows the remaining exit counter. Thaw fades
  the opacity and then removes the material. The counter digits are a screen-space UI Toolkit label positioned
  from the block's projected position; frozen blocks do not move, so the
  label updates only on board layout changes. One ice material exists.
- All screen-space UI (Home, Settings, HUD, pause, fail, and win popups) and
  the level editor window use UI Toolkit (UXML, USS, `UIDocument`,
  `EditorWindow`), including projected block labels. No new UGUI canvases or
  TextMeshPro UI. The `com.unity.ugui` package stays
  only because the Input System UI module needs its `EventSystem`.
- All player tools are **Boosters**, with one shared definition and application
  system. Four HUD choices are Time Freeze, Rocket, Hammer, Vacuum; two
  pre-level choices are Extra Time and Rocket. Rocket has one effect, with
  random target acquisition at opening and player target acquisition in-game,
  but two persistent stock counts: the pre-level Rocket is its own
  `StartingRocket` definition, never counted in the in-game Rocket's pool
  (DEC-167). Do not create a separate Skill system.
- Hammer removes the tapped block whole, whatever its footprint, including
  an active Ice shell and the block under it (DEC-147). It never splits a
  block and raises one `BlockRemoved`. Rocket removes one 1x1 cell; the
  remaining 4-connected parts become independent blocks with new runtime IDs
  (DEC-146). The final or only cell of a block is refused, so Rocket never
  destroys a whole block.
- Which board booster may target a block with a given effect is data: the
  `Data/Boosters/BoosterRestrictionMatrix.asset` rows (Rocket, Hammer,
  Vacuum target kinds) by block-effect columns (Ice, Arrow, ...). The shipped
  matrix closes only Rocket on Ice (DEC-171). A closed cell refuses the
  crosshair, the tap, the opening Rocket and the command itself, and Vacuum
  leaves restricted blocks of its colour on the board.
  Recomposition uses prewarmed pools bounded by reachable authored-cell
  footprints, independently of initial stock. Restart restores the authored
  board, not inventory. The Hammer cast uses the Blender-authored 3D mallet
  now imported as `Assets/ColorBlockJam/Prefabs/Boosters/Effects/HammerEffect.prefab`.
- Time Freeze stops the countdown on committed application for 10 seconds of Playing time,
  granting 10 extra seconds to play without also adding 10 to the countdown.
  Its separate HUD indicator counts 10 to 0 while the main timer stays held.
  Pause preserves both clocks. On expiry within a tick, only the remaining
  delta advances the main countdown. Both text displays change only on an
  integer-second change using prebuilt strings. The Shader Graph frost follows
  the freeze duration. Pre-level Extra Time is a separate numeric

## Performance Rules

Optimization is a first-class requirement, not a polish step. Each rule names
the technique, where it applies, and how it is verified.

1. **One shared opaque art material, color through `MaterialPropertyBlock`.**
   Blocks, walls, gates, ground, arrows and the Hammer and Rocket booster model LODs
   share `MAT_Gameplay` and the URP 14 Board Lit shader (the unused 3D Vacuum model
   was deleted on 2026-09-28; the Vacuum is its baked sprite, `Prefabs/Boosters/Models/Vacuum.prefab`). The 128 x 32 atlas contains eight
   ordered booster swatches, one cell per `PaletteColor`, its light door-arrow
   blend and the arrow colour; every board tile (blocks, walls, floor, gates,
   arrows, exit fragments) selects its cell through `_PaletteUV`, and the shader
   has no colour property. The atlas is authored art; `GamePalette` only names
   each colour's cell (DEC-202). Instanced UV scale/offset preserves the original meshes
   and their UVs. `Art > Update Shared Art Material` regenerates the atlas and
   prefab bindings. Vacuum's baked transparent animation retains its separate
   sprite material/sheet. This supersedes DEC-96's separate opaque booster
   material boundary on the user's 2026-09-25 request; see the
   [shared art report](docs/art/shared-art/README.md).
   The shader has explicitly GPU-instanced color/clip properties. One
   view owner composes every renderer's cached MPB; tint changes only on
   spawn/recolor, and owned effects update only changed values. Views never
   read a palette: the block factory resolves colours through `BoardArt` and
   the environment composer through `EnvironmentDatabase`, a tile's owner's
   `SetColor` is its only colour write, `SetClipPlane` (exit and effect
   clipping) and `SetIceValues` (a frozen block's Ice pass, DEC-184) its only
   other MPB writes, and a pool release makes none; tiles
   cache their MPB while the block is prepared (DEC-123). No material
   instances or per-renderer polling. Adapt Pixel Flow's pattern and use CBJ
   Template for the look, as specified in DEC-96 and
   [Rendering Reference Review](docs/Rendering-Reference-Review.md).
   MPB renderers bypass SRP Batcher. Compare against a prebuilt per-color
   palette with no MPB on ordinary block renderers; include any effect-time
   MPB exceptions and their batching cost. An instancing checkbox does not
   combine both batching paths. On the same level 5, quality and device,
   record batches, SetPass, instancing/break reasons and CPU/GPU frame cost.
   Keep one path with lower measured device frame cost within NFR-P4 budgets.
2. **Sprite Atlas for UI.** Every sprite under
   `Assets/ColorBlockJam/Art/UI` is packed into Sprite Atlases (one for Home
   and Settings, one for the HUD and popups).
   UI Toolkit reads atlas sprites as backgrounds; the panel's dynamic atlas
   stays on. Verify the Home screen and HUD batch counts with the Frame
   Debugger and record them.
3. **Onity pools own board objects.** Block views, door views, arrows and
   effect visuals come from Onity pools (`OnityObjectPool`,
   `PrefabComponentPool`). One disposable scene-scoped owner creates and
   disposes the pools; `BindPooledFactory` is not the lifetime owner. Pools warm up at level load
   to the level's counts, `IPoolHooks` `OnPoolGet` and `OnPoolRelease` reset
   state, and teardown returns every object. No `Instantiate` or `Destroy` inside an
   attempt. Verify with Onity pool diagnostics and a Profiler capture that
   shows no instantiation during play.
   Block roots must be obtained through `BlockPieceFactory`, an Onity
   `IFactory<BlockPieceSpawnData, BlockPiece>` backed by `PooledFactory<BlockPiece>`
   and one `PrefabComponentPool<BlockPiece>` of the catalog's block root (DEC-193). The attempt
   owner calls `Prepare(count, cellCapacity)` before Playing, `Create`/`Return`
   during use, and `Dispose` at teardown. A prepared root starts empty and takes no
   tiles until `Create` gives it its cells. Root exhaustion rejects instead of growing.
   Roots hold no tiles of their own: every root shows tiles from the factory's one
   shared `BoardTilePool` (one pool per piece kind under one "Board Tiles" object),
   takes exactly the tiles its footprint shows and returns them on recompose and
   return (DEC-184, revising DEC-120's per-root pools). `WarmTiles` fills it on Home
   with every block's own tiles plus a small spare: the most extra tiles of each
   kind that one block can need after any Rocket removals, splits included
   (`BlockPieceCapacity.AddTileBudget`, enumerated up to 12 cells). This is the one
   stated exception to "no `Instantiate` inside an attempt": on the user's order, a
   need beyond that budget (several blocks split before any tile comes back)
   instantiates the missing tiles, and they stay in the pool.
   Floor, wall, corner and door environment pieces are pooled the same way,
   placed through the BoardRoot `Grid`; no Tilemap or RuleTile instantiates
   anything. The environment is composed once per level on `Home` (before `Playing`), stays
   immutable and survives Restart of the same level; a level change or scene
   disposal returns every piece and disposes the pools.
   `IPoolHooks` reset cells, tint, clipping, ice and root transform,
   and return the root's tiles to the shared pool. Return uses immutable pool ownership, even after a
   booster changes the current shape. Level footprints are copied into
   checkout data; direct runtime Instantiate of a block root is prohibited.
4. **Onity owns the tick.** Exactly one object, the session's tick owner,
   implements `IOnityTickable` (`Tick()` runs once per frame from the Onity
   context's `Update`). It advances the plain C# gameplay systems in a fixed
   order and only while the state is `Playing`. Gameplay systems expose a
   `Tick(float deltaTime)` method and never implement `IOnityTickable` or a
   MonoBehaviour `Update` themselves. Verify with the Profiler that no
   gameplay tick sample appears outside `Playing`.
5. **Zero per-frame allocation.** The `Playing` tick path (drag, move, timer,
   view sync) allocates 0 B in steady state. Queries are plain loops over
   arrays and lists, text uses ZString or prebuilt strings, and Newtonsoft
   never runs in a `Playing` tick. Verify with the Profiler's GC Alloc column
   over 10 seconds of play on the Android device and record it.
6. **Nothing third-party runs unattended.** The README lists every runtime
   loop that Onity, PrimeTween, or a Unity package starts, who owns it, and
   how it stops. MCP for Unity and other dev tooling stay out of player
   builds. Cinemachine, ProBuilder, Timeline and Visual Scripting were unused
   and were removed on 2026-09-29 (DEC-185); `PlayerBuildAssemblyFilter` keeps
   MCP for Unity's runtime assembly out of every player build.
7. **Explainable code.** Every class states its single responsibility in one
   sentence at the top, and every non-obvious choice points to a decision
   row. Code that cannot be explained as "this does X, it is here because Y"
   is rewritten.
8. **Allocation-free libraries, used where they belong.** `System.Linq`
   stays out of the Domain and Presentation assemblies (an import there
   fails code review); queries are plain loops, and ZLinq, which nothing
   used, was removed on 2026-09-29 (DEC-185). ZString or prebuilt strings
   replace `string.Format`,
   interpolation and `StringBuilder` for runtime HUD and popup text and for
   editor text rebuilt per frame, repaint or pointer move; one-shot editor
   messages, tooltips, dialogs and validation sentences may use
   interpolation (DEC-179). The timer reads prebuilt `m:ss` strings.
   Newtonsoft Json.NET reads the level manifest at scope startup and a
   level pack on Home (DEC-196), and serializes editor level changes and
   player saves outside a `Playing` tick.
   Owned writes in Home, Paused and terminal states
   are outside this hot path. Verify with the Profiler's GC Alloc column (0 B
   in `Playing`) and a grep for `System.Linq` and `string.Format` in the
   gameplay assemblies during the code-quality gate.
