## 1. Layout

The user's sentence and the photo read as a **left | right** split: a full-height tools column on the left, and on the right the level selection with the drawing canvas directly under it. That is the two-part editor. (Open decision 1 confirms it.)

Play Mode's scene change stops `LevelPreviewOwner` through `sceneClosing`, and the reopen raises no scene event, so the owner listens again on `EnteredEditMode` ([Level Editor Scene Preview](Level-Editor-Scene-Preview.md#lifecycle)).
  - Tests: `LevelTestPlayTests` (request, lookup, start/finish and refusals through replaced steps, the button order, save-first, and Stop Test's label, enabled state and exit step through the Play Mode states) and the explicit `LevelTestPlayRoundTripTests` (real Play Mode round trip; run it by name).

Selection is left-click with Select. The canvas is `focusable = true` and calls `Focus()` on pointer down so keys reach it; shortcuts are ignored while a text or integer field has focus.

### Colour order (2026-09-26, `TASK-20260926-145804549-da16f02f-level-editor-color-order`)

User decisions of 2026-09-26: the order recolours the level ("Level'ı yeniden renklendir"), and Color Switch trades the selected colour with a random one ("Rastgele renkle takas"). The buttons first sat under the canvas; the user's second revision ("Renk butonları Colors altına", "40 px, iki satır") puts them under the Colors swatches and makes the swatches 40 px in two rows.

**Board-only recolour (user orders of 2026-09-27: "reset order kaldır ve shuffle renkleri editör panelinde değiştirmesin sadece board da renkleri değiştirse yeterli", "evet sadece board boyasın color switch de").** Reset Order is removed. Color Shuffle and Color Switch recolour only the level on the board (`RecolorLevel`): the draft's order, and with it the swatch grid, the badges and the Pen keys, no longer change. No button changes the order any more, so it stays palette order unless a kept draft brings an older order back. The order model and its draft field remain; removing them is a separate cleanup. The bullets below describe the mechanism; where they say a button changes the order, this paragraph supersedes them.

- **Order and badges.** `LevelColorOrder` (plain C#, immutable) is a permutation of the 11 gate colours; the default is palette order.
  - Each Colors swatch shows its 1-based position in a framed badge at its top-right (`badge-<Colour>`, 14 px high, 10 px text). The badge ignores the pointer and is absolutely positioned, so the swatch keeps its click, hover, tooltip and 40 px two-row layout. Badges stay hidden until the window calls `SetOrder`.
  - `SetOrder` also moves each swatch to its order position (user request of 2026-09-26: "shuffle yapsak da veya switch buradaki sayılar aynı kalabilir"). After Color Shuffle or Color Switch the colours change places and the grid's badges still read 1 to 11. `[` / `]` step through this grid order (palette order without a draft).
- **Level design use.** Every block pairs with gates of its own colour, and a change of order is a one-to-one colour map. Geometry, pairs, difficulty and the `LevelData.Validate` result therefore stay the same; only the look changes. Designers get colour variants of a proven layout, distinct looks for consecutive levels, and a quick fix when similar colours sit side by side.
- **Recolour rule.** `LevelColorRemap.Apply(level, from, to)` gives the colour at position k of `from` the colour at position k of `to`.
  - It covers every block and door `colorId` and every effect parameter the `LevelEffectRegistry` types as `PaletteColor` (single or comma list) on blocks, doors and board objects, for example `colorSequence`, `colorA`/`colorB`, `outerColorId`, `ropeColors`, `tokenColorId` and a board object's `colorId`.
  - Values that are not gate colours (Wall, neutral, unknown text) and effects of an unknown type stay unchanged.
  - `GetUsedColors` walks the same fields through an identity map, so the two never disagree about where colours are.
- **Action row** (`color-order-actions`, in the Colors group directly under the swatches): two buttons, each with its white icon (16 px) and its name (11 px text). They share the row's width, and a narrower tools pane wraps them. Each is one undo step, and the status line names the moved colours, for example "Colours: Red → Purple, Blue → Yellow."
  - **Color Switch** (`color-switch`, fifth revision, user order of 2026-09-26: "kırmızı bir parçaya tıklayıp switch yaparsam bütün kırmızıları değiştirmeli"). The source colour A is the colour of the clicked element: the block the Pen edits, or with Select a chosen block or gate. It is not the tool colour. `LevelColorRemap.PickSwitchPartner` picks B at random from the gate colours the level does not use, and from every other colour only when none is unused. A and B trade places everywhere in the level (not in the order, since 2026-09-27), so every A block, gate and effect colour becomes B. The tool colour becomes B. With nothing chosen, nothing changes, no undo step is recorded, and the hint box says "Click a block, then press Color Switch." (`k_switchHint`).
  - **Color Shuffle** (`color-shuffle`): a random one-to-one recolour of the board that moves at least one colour the level uses. A draw that keeps every used colour moves the first used one. The order stays.
  - Reset Order (`reset-order`) was removed on 2026-09-27. Undo returns earlier colours.
  - Both are disabled while no level is loaded.
- **Pen colour keys** (user answer of 2026-09-26, "Pen only: 1-9, 0, -", `TASK-20260926-180414067-b923c8a9-level-editor-pen-color-keys`). While the Pen is active in any use (plain, editing a block, "+ New piece", Barrier brush), `1`-`9` pick the colour whose badge shows 1-9, `0` picks 10 and `-` picks 11, top row or keypad (`LevelColorKeys`). The colour comes from the draft's order (palette order without a draft), so after Color Shuffle key 1 picks the new first colour. The key runs the swatch click's `PickColor`: tool colour, outline and one "Recolour Block" step for the block the Pen edits, nothing when the colour is unchanged. Shift is ignored; Ctrl, Cmd and Alt combinations and text fields are not shortcuts. Outside the Pen, `1` `2` `3` still pick Select, Pen and Eraser and the other colour keys do nothing. The Pen and Colors tooltips name the keys, and `SetOrder` sets each swatch tooltip to its own key ("Red: key 3 with the Pen ([ / ] cycles)") from prebuilt texts. Tests: `LevelColorKeysTests`.
- **Draft, undo and reload.** The order is `LevelDraft.m_colorOrder` (empty = palette order), set through `ApplyCommand`'s `alsoApply`, so one undo step moves a recolour and its order together.
  - `GetColorOrderText` joins the draft-change check (`IsDraftOutOfSync`, `m_syncedDraftJson`), so undoing an order change refreshes the badges. It is not part of the unsaved-changes check (`HasDraftChanges`), because the order is never saved: counting it would keep the window unsaved after Save.
  - So an order change that moves no colour the level uses leaves no unsaved change. Color Switch always moves the clicked colour, so it always leaves one. A reload then drops it and the badges return to palette order; the level is unaffected.
  - `ReloadCopy` carries the order through a script or domain reload. A copy kept before the order existed reads as palette order.
  - Loading a level (another level or database, Reload, Restore) resets it to palette order.
- **Icons.** `color-switch` and `color-shuffle` in `Editor/Levels/Icons` are the user's 512 px masters (`docs/art/level-editor-icons/source`) turned into white 64 px icons that keep the source alpha, with the other icons' import settings (Editor GUI, no mipmaps, bilinear, clamp, max 64, uncompressed).

### Gates, edges, walls and issues (2026-09-25, `TASK-20260925-082521487-465fec81-level-canvas-gates-edges-walls`)

This section supersedes the Doors row's separate Door tool and the Board row's field-only resize.

- **Pen gates.** With the Pen, a click on the wall ring, or a drag along one side, paints gates in the selected colour.
  - A gate spans 1 to 3 cells (user rule of 2026-09-25). `LevelEditCommands.k_maxDoorLength` refuses a longer extension or merge, and the issues list warns about a longer gate until `LevelData.Validate` enforces the rule (schema task `f7bfcf6a`).
  - The ghost shows each segment in that colour, or red where another colour's gate is. Once a segment is refused, the rest of the stroke also shows red.
  - A press on a ring corner shows "A gate cannot sit on a corner; paint it along one side."
  - Switching tool mid-stroke drops the stroke unpainted.
  - On release the window applies the whole stroke as one undo step (`Paint Gate`):
    - Each segment calls `LevelEditCommands.TryPlaceOrExtendDoor`, which adds a gate, extends a touching same-colour gate, or merges two of them. The door earlier in the list keeps its id.
    - Segments the same colour already holds are kept.
    - Another colour's gate stops the stroke with "The Top edge at 1 already holds door d1."
  - The painted gate becomes the selection but not a choice (`m_doorChosen`), like a just-placed block. A swatch picked for the next piece never recolours it.
- **Gate edits.** The Eraser (left or right click) and a right click with Select or a transform tool remove the whole gate (`TryRemoveDoor`). Select a gate by clicking it, then a swatch recolours it (`TryRecolorDoor`) and Delete removes it.
  - **Pen right click** (user request of 2026-09-27, `TASK-20260926-212320311-949d4415-level-editor-pen-gate-segment-remove`): with the Pen, including its Barrier brush and freehand modes, a right click on a gate takes only the clicked segment off as one undo step ("Remove Gate Part"). The canvas raises `DoorSegmentRemoveRequested` (door index, side, segment) instead of `DoorRemoveRequested`, and the window applies `LevelEditCommands.TryRemoveDoorSegment`.
    - An end segment shrinks the gate by one; it keeps its id, colour and effects.
    - The only segment of a one-cell gate removes the gate.
    - A middle segment splits the gate into two gates of the same colour on the same side (the contract's default). The part before the segment (lower segment index) keeps the list index, id and effects. The part after it is added at the end of the list with the lowest free id (`GetNextDoorId`) and no effects, because gate effects are hand-written, outside the case scope, and the editor cannot add them.
    - Every other gate keeps its order and id. A stale door index, another side or a segment outside the gate is refused and changes nothing.
  - The Pen tooltip says a right click takes one gate cell off and the Eraser removes the whole gate.
- **Edge controls** (reference layout, user request of 2026-09-25).
  - The controls form one frame, as in the reference (user feedback of 2026-09-25): each side has two 22 px bars, 6 px apart, in a 58 px band outside the gate bars, and both run past the board over the wall ring to 6 px short of the corner block. The inner bar (arrow into the board) removes the edge line; the outer bar (arrow out) adds one. The arrows are the user's chevron icons (`docs/art/level-editor-icons`, white copies in `Editor/Levels/Icons`, skin tint). `LevelCanvasGeometry.k_edgeButtonBand` is reserved in the fit.
  - Each corner is a 2 x 2 block of the frame: the fill button (22 px square) where the outer bar row and column cross, the cut button where the inner ones cross. The outer fill button shows its own corner's bracket (pointing out), the inner cut button the opposite bracket (pointing in), like the bars' arrows. They carve or restore void corner cells (`TASK-20260925-135325403-e7f5beb8-level-canvas-corner-voids`, user report "void ekleme çalışmıyor"): the cut button turns the board's corner cell into a void cell as one undo step ("Cut Corner"), the fill button turns it back ("Fill Corner"). Cut is disabled, with the reason in its tooltip, when a block, a board object or a gate on the cell is in the way; fill is enabled only on a void corner. The walls come from `EnvironmentComposer` with the level's void cells, so they wrap the cut corner exactly as the play area builds it. Commands refuse a block cell on a void ("Cell (x,y) is a void.") and a gate in front of one.
  - Staircase corners (`TASK-20260926-181022947-224a7aef-level-canvas-staircase-corners`, user request of 2026-09-26: "önünde engel yoksa küçültüp büyültebilmeliyiz"):
    - Each further press of a cut button cuts the corner's next square step (DEC-190, user report of 2026-09-29: the diagonal staircase could never make a square notch): first the corner cell, then the L-shaped ring of its two neighbours and the cell between them (a 2 x 2 notch), then the next ring of five cells (3 x 3).
    - Each fill press turns the last step back into floor. Every press is one undo step. A step is restored when one of its cells touches floor, since a ring is connected.
    - `LevelCornerSteps` defines step k as the cells at Chebyshev distance k - 1 from the corner (an L-shaped ring, clipped to the board). The corner's depth is how many leading steps are all void, read from the void cells every time and never stored, so Undo, the reload copy and a reloaded JSON agree. A level saved with the earlier diagonal staircase reads as a shallower notch, and its next cut fills the missing cells of that square.
    - A step is cut whole or not at all. Each still-floor cell must be free of blocks, board objects and gates opening onto it, and the whole step together must leave one four-connected floor with at least one cell. Otherwise cut is disabled and its tooltip names the first reason (for example "Block b1 covers the corner step cell (1,0).").
    - The first step keeps the single-cell rules and messages. The enabled tooltips give the cell counts ("Cut the next corner step (3 cells).", "Fill the last corner step (2 cells) back with floor.").
    - A fill on a Wall-brush void that lies on the last step fills it with the step.
  - After v2, a bar click works one cell at a time: an inner click voids that edge cell, and an outer click adds one, growing the board with the rest of the new line void. That follow-up is its own task.
  - `LevelEditCommands.TryResizeBoard(level, side, delta)` handles every size change:
    - Left and Bottom shift block origins and the perpendicular gates, so content keeps its place. Right and Top only resize.
    - A removed line drops the blocks that have a cell in it.
    - A perpendicular gate that crosses the removed line is shortened, or removed when nothing of it remains.
    - Gates on the shrunk side stay on that side and follow the edge, as they already do when Right or Top shrinks.
    - A void cell on the resized side's outermost line follows that edge instead of shifting with the rest of the content, so a cut corner stays a corner through growth and shrink, unless its new cell cannot be void (covered by a block or board object, already void, a gate opens onto it, or the floor would split), in which case it is dropped (`TASK-20260925-144031187-141dd370-resize-keeps-edge-voids`).
    - A staircase of two or more steps at one of the resized side's two corners follows its corner instead (task 224a7aef), so the edge rule and the shift cannot tear it into a notch in the middle of an edge. It is laid again at the new corner, step by step outward under the cut's rules, and the first step that no longer fits ends it. A single cut corner, the other sides' staircases and voids outside a staircase keep the rules above.
  - A change that removes content is hatched on the canvas: the removed lines, every cell of a block that goes with them, and the gate segments lost.
  - The inline `resize-confirm` row asks `LevelResizeReport.Describe()` ("Remove 1 block and shorten 1 door?") and applies one undo step on Apply. Cancel or Esc leaves the draft unchanged.
  - The inline row replaces a modal dialog so the hatch stays visible while the designer decides.
  - The bars disable at 3-8 x 3-10. The Width and Height fields were removed in the tools cleanup, so the bars are the only resize.
- **View.** The mouse wheel zooms about the view centre, and a middle-button drag (or Alt+drag) pans. Home resets the view.
  - Zoom is relative to the fit, the size at which the board, gate bars and edge controls fill the canvas. The first view is `k_defaultZoom` (0.85 of the fit), leaving a margin.
  - Limits follow the grid size: the farthest view is half the fit, and the closest shows about `k_closestCellsAcross` (3) cells across the canvas (`GetMaxZoom`). Cells stay at least 18 px.
  - Hit tests, gate bars and edge controls all follow the zoomed geometry.
- **Rule-set walls.**
  - `LevelCanvasWalls` composes `EnvironmentComposer` output from a `BoardLayout` with the board size and only the gates that pass `BoardLayout` validation, so an invalid gate never removes walls.
  - The rule-output placements become `LevelWallGlyph`s:
    - a straight `Wall` fills its quadrant;
    - a `Corner_1` is a quarter disc rounded toward its yaw (0 = (+1,+1), clockwise).
  - Composition runs once per draft change. `ColorBlockJam.Editor.asmdef` references `ColorBlockJam.Environment` (user-approved).
  - A missing or invalid environment database is one "Walls: ..." warning and no walls. The old fixed ring band is gone.
- **Issues list.**
  - `LevelDraftIssues.Collect` gives located issues. Errors mirror `LevelData.Validate` exactly (an agreement test covers the database levels and 400 random drafts). Warnings cover play-only problems: non-gate colours, a block colour without a gate, and `BoardLayout` failures.
  - PRE-1 for Arrow blocks (catalog BLK-01, AC-BLK-01.5, DEC-158, `TASK-20260926-230921278-a3ffdc40-arrow-block-gameplay`): an Arrow block that has a gate of its colour somewhere, but none on its two axis sides within the rows (Horizontal: Left or Right edge) or columns (Vertical: Top or Bottom edge) it spans, gets one warning outlining the block: "Block {id} can never exit: its {Axis} arrow needs a {Colour} door on the {Left or Right | Top or Bottom} edge within {row r | rows a-b | column c | columns a-b}." It is a static check, not the solver (a gate that is too narrow or out of reach still passes), and a warning, so Save Level stays allowed. A block with no gate of its colour at all keeps only the broader "can never exit" warning. `ArrowIssueTests` covers 1x1, I3 and L3 on both axes, with and without the gate.
  - `LevelEditorIssuesList` ("Issues (n, e blocking Save)", at most 120 px, under the canvas) outlines the picked issue's cells and gate span on the canvas.

### Obstacles (2026-09-25, `TASK-20260925-145628329-306ba760-level-editor-obstacles-wall`)

This section supersedes the Board row's Void paint and the void-paint item of `TASK-20260924-230915891-b289bba3-level-canvas-v2-tools`.

- **Section.** The column now reads Tools, Colors, Blocks, Obstacles, Edit, Raw data (superseded on 2026-09-26: Edit moved under Tools, see Tools cleanup). The `obstacles-group` foldout ("Obstacles") sits directly below Blocks and starts open.
  - It holds one tile, Wall (`obstacle-wall`): a swatch in the palette's Wall colour above the word "Wall". Its tooltip is "Wall: paints permanent interior wall cells (level void cells). Left drag paints; the Eraser or a right drag restores floor."
  - While armed, the tile has the tool buttons' blue fill and white frame.
  - Superseded: a Block (Solid Block) brush from `TASK-20260925-160721096-2c8da893-solid-obstacle-art` replaced the Wall tile, and the user then removed Block too (2026-09-25). The section now holds only the Barrier tile ("Obstacles: Barrier" below). The void commands (`TryPaintVoid`, `TryEraseVoid`, corner cut and fill) stay; the Eraser still restores walled cells.
- **Arming.** Wall arms the Pen with the Wall brush (`LevelEditorToolState.ArmWall`, `IsWallArmed`). It is a Pen brush, so `LevelEditorTool` gets no new value.
  - Picking a piece, Select, the Eraser or a transform tool disarms it. The Pen button and key 2 keep it armed.
  - The Pen badge takes the Wall colour while the brush is armed.
- **Painting.** With the Wall brush, a left press and drag over board cells builds one stroke.
  - The canvas walks from cell to cell through shared sides, so a fast drag leaves no gap. Each board cell joins the stroke once. On release the canvas raises `WallStrokeRequested`; it changes nothing itself.
  - The window applies `LevelEditCommands.TryApplyVoidStroke`, which calls `TryPaintVoid` for each cell. `TryPaintVoid` decides with `GetVoidIssue(level, cell, "cell")`.
  - Cells that are already walls are kept. A refused cell is skipped, the rest applies, and the status shows the first refusal, for example "Block b3 covers the cell (2,1)."
  - Passes repeat while one changes a cell, so the stroke's order does not matter. A dead-end cell can be walled before the cell in front of it.
  - A stroke is one undo group ("Paint Wall"). A stroke that changes nothing records no step.
- **Restoring floor.** An Eraser click or drag on board cells, or a right drag with the Wall brush, restores walled cells as one undo group ("Erase Wall").
  - Each cell goes through `TryEraseVoid`, which accepts any void cell, a cut corner included. It refuses a cell with no floor next to it, which would leave a floor island; a later pass of the same stroke retries it.
  - An Eraser click or a right press on a block or gate still removes it (the one right-click rule).
- **Ghost.** With the Wall brush, the hovered cell is green where `LevelCanvasModel.CanPaintWall` holds and red elsewhere. The stroke ghost covers the cells that are not walls yet. An erase stroke, and the Eraser over a wall, mark the wall cells green.
  - `CanPaintWall` is computed once per model from `GetVoidIssue`, so the wall ghost is red on blocks, board objects, gate cells and cells that would split the floor. The block ghost keeps `IsFree`, which since `TASK-20260925-102907480-9e5cbf34` refuses a closed barrier cell exactly as the block commands do.
- **Wide walls.** A wall area 2 x 2 or larger gets a solid top from the environment (`TASK-20260925-160721096-2c8da893-solid-obstacle-art`, decision 4(b)), so a wide stroke applies with no warning.
- **Drawing and data.** No wall drawing was added. A walled cell is a level JSON v2 `board.voidCells` entry, drawn as a floor gap wrapped by the `LevelCanvasWalls` rule-set glyphs, which are recomposed after each stroke. The LevelEditor scene preview rebuilds from the draft (DEC-102).
  - The reference 17 Level 32 wall at (1,1) and (2,1) is a test fixture only (decision 5(a)). It is not added to the active database.

### Obstacles: Barrier (2026-09-25, `TASK-20260925-102907480-9e5cbf34-level-editor-obstacles-barrier`)

Catalog OBJ-05. User decisions of 2026-09-25: only the official Barrier stays in Obstacles; the Block tile and the section's "Starts open" checkbox are removed, and `startsOpen` is edited as an effect param in the Effect Editor.

- **Tile.** Obstacles holds one tile, Barrier (`obstacle-barrier`): a hatched swatch in the Wall colour above the word "Barrier". Its tooltip (`LevelDatabaseWindow.k_barrierTooltip`) names the rule: closed cells are walls, open cells are floor, and the barrier flips after every cleared block.
- **Brush.** Barrier arms the Pen with the Barrier brush (`LevelEditorToolState.ArmBarrier`, `IsBarrierArmed`, `LevelObstacleBrush.Barrier`); `LevelEditorTool` gets no value. A piece, Select, the Eraser or a transform tool disarms it; the Pen button keeps it. Inside the Pen, key 2 picks badge colour 2 and also keeps it armed (`TASK-20260926-180414067-b923c8a9-level-editor-pen-color-keys`). The Pen badge takes the Wall colour.
- **Painting (`LevelBarrierCommands.TryApplyStroke`).** A left drag walks cell by cell like the other obstacle strokes. On release, each connected group of new floor cells becomes one barrier with a fresh `barrier-{n}` id and no params, so it starts closed.
  - A group that covers or touches existing barriers joins them. Merge rule: the first-listed barrier keeps its id and whole effect (its `startsOpen` and any other param); the others are removed.
  - Void cells and other board objects are skipped, and the status names the first ("Obstacle o1 occupies that cell.").
  - A closed result over a block cell refuses the whole stroke with the validation's message, for example "Level L cell object barrier-1 effect barrier starts closed on block b1 at (1, 3)."
  - One stroke is one undo group ("Paint Barrier"); a stroke that changes nothing records none.
- **Erasing.** The Eraser, a right drag with the brush, or a right click on a barrier cell removes barrier cells as one undo group ("Erase obstacle"). A barrier that falls apart splits into connected barriers with the same effect; the first keeps its id and the others get new ids. An empty barrier is removed. The Eraser also restores walled (void) cells in the same stroke.
- **Starts open.** No Level Editor control. `LevelBarrierCommands.TrySetStartsOpen(level, objectIndex, bool)` sets the param for the Effect Editor, refusing to close a barrier over a block with the validation's message.
- **Canvas.** `LevelCanvasModel` keeps each board object (`LevelCanvasObstacle`: id, cells, barrier flag, `StartsOpen`). Barrier cells draw above the floor and walls and below doors and blocks as a hatched Wall tint: dark while it starts closed, light while it starts open, with the barrier's outline. The canvas repaints only on change.
- **Selection.** `LevelCanvasSelectionKind.Obstacle` (`LevelCanvasSelection.ForObstacle`). The hit test reports a board object's index on a Cell hit when no block covers the cell. The Select tool on such a cell selects the object, outlined in white, and never drags it; Selected Block reads "Obstacle {id}". The selection is resolved by id after every draft change.
- **Blocks and barriers.** A block may sit on an open barrier cell but not on a closed one. `LevelEditCommands` place, move and cell replacement refuse a closed barrier cell with the validation's message, and `LevelCanvasModel.IsFree` uses the same check, so the ghost matches. Freehand strokes and Re-stamp keep their stricter rule: no board object at all.
- **Save gate (decision 3(a)).** Until `TASK-20260925-103527585-3d1b0a34-barrier-rule` implements the barrier, Save Level refuses a level with a barrier: it writes nothing and the status shows `LevelData.ValidateRuntimeSupport`'s message ("Level L cell object barrier-1 effect barrier is not implemented in gameplay yet."). `LevelBarrierCommands.GetSaveIssue` asks about barriers only, so other levels save as before; the check passes with no editor change once the rule lands. The draft and the preview keep the barrier.

### "+" level pieces and the Piece Editor link (2026-09-25, `TASK-20260925-082521498-8e54a900-level-editor-custom-pieces`; identity by key since DEC-193)

A level piece belongs to the levels that use it, not to the piece library. It lives only in its blocks' cells, so it reaches players inside level JSON without a client update, and its name lives in the level's `pieces` table ([Level Data Format](Level-Data-Format.md#level-piece-names), section "Shape identity").

- **Identity (DEC-193).** A block stores no shape id: its piece is the `ShapeKey` of its cells (`LevelBlockData.Key`, the same for all 8 rotations and mirrors). A key the piece library holds is that template; any other key is a level piece. Piece limits: at most 25 edge-connected cells inside 5 x 5 (`LevelCustomPiece.TryValidate`, the same rule as `LevelData.Validate`). Transform `t` mirrors horizontally when `t >= 4`, then turns clockwise `t % 4` times through `LevelPieceTools`, so it means the same as R and F.
- **"Use the existing one".** Placing, drawing or re-stamping a shape that already exists reuses it, by key:
  1. A library key is that template: its tile shows the template's display name, no level-piece tile appears and no name is written.
  2. A key another level of the same database uses is listed already; Save Level copies that level's name into this level's `pieces` table when this level has none.
  3. A key that exists only in another level database has nothing to look up.
  4. A new key becomes "<Level Name> Piece n" with the lowest free n, unique ignoring case among the database's names, the library's names and this session's piece names (`LevelNamedPiece.GetDefaultName`); Save Level writes it. A level name too long for a 128-character piece name gives "Level Piece n".
- **Piece names (`LevelPieceNames`).** `LevelSaveController.Prepare` gives the level as written the table `LevelPieceNames.Resolve` returns: one entry per key a block uses and the edit catalog (the library with its pending template footprints) lacks, in block order, with the level's own name for it, else another level's, else the name this session gave the piece, else a new default. Names for other keys are pruned. After the write the saved level becomes the draft without an undo step (`LevelDraftController.SetSavedLevel`), so the draft reads clean and keeps its undo history. While the piece library cannot be read, the level keeps its own table. An edit that moves every block of a piece to a new key moves its name with them (`LevelPieceNames.CarryName`); a new key that has a name of its own keeps it, and a template key takes none.
- **Blocks palette.** After the template tiles, a full-width "Level pieces" header (`custom-pieces-header`) starts the level piece section (`LevelPieceEditController.RefreshCustomPieces`).
  - It lists the open level's level pieces in block order, then this session's pieces of the open level that no block uses yet (drawn only in the Piece Editor), then the database's other levels' pieces (the first level that uses a key names it). A key the edit catalog holds is never listed.
  - Each tile shows the piece's name under a centred thumbnail, at a cell size no larger than the library's; the key shows only in the tooltip ("{name} (key 00008E2): a level piece. …"). A tile arms its piece for placing with Select, like a template tile. Element names carry the key: `shape-<key>`, `slot-<key>` and `delete-shape-<key>` for templates, `custom-<key>`, `custom-slot-<key>` and `delete-custom-<key>` for level pieces.
  - Each level piece tile has the red × as well (user request of 2026-09-26, `CustomPieceDeleteRequested`). After the designer confirms (`ConfirmPieceDelete`), every block of the open level with the piece's key is removed as one undo step ("Delete Level Piece"), so the tile goes with them and Undo brings both back. A piece no block uses (drawn only in the Piece Editor) is forgotten. A piece only other levels use is not changed; the status names those levels, because other levels are not in this level's undoable draft and are written only by their own Save Level.
  - The last item is the "+" tile (`create-level-piece`): the plus glyph over the label "New piece", with no icon. It is kept out of `m_tiles` and `m_choices`, so library tile indices stay library indices. Without level pieces, it follows the template tiles.
  - Piece Type lists the templates by name and shows a level piece's block as "<name> (level piece)".
- **Tracked level pieces ("+" New piece, `LevelNamedPiece`).** User order of 2026-09-25 (contract revision): one "+" click makes one level piece of the open level.
  - The window session tracks each level piece it draws, edits with the Pen or shows in the Piece Editor. A piece's key changes with every stroke, so its identity is a session token `piece:<scope>:<tag>-<n>`; the tag is new for each session, so a token that a closed window's Piece Editor still shows never names a piece of a new session. It keeps the level scope `<databaseGuid>/<levelId>`, the name it was given, its footprint and the block its strokes draw. `LevelPieceSession` keeps it across a domain reload.
  - A "+" piece takes the default name of rule 4. The Level pieces section lists it under the level's name for its key (else the session's) once it has a footprint, and its thumbnail follows the drawn block after every change, undo and redo included.
  - **Its blocks (DEC-193).** While a key is only on its way, during a drawing, it says nothing about who a block belongs to. A tracked piece therefore records its blocks (`LevelNamedPiece.MemberIds`): the blocks with its key when an edit of it starts (a Pen click on one of them, `StartPenEdit`; a tile click, `GetTileMirror`), the block it draws (`PlaceFirstCells`) and the blocks placed from its tile or given it through Piece Type (`JoinPlacedBlock`). Only these follow its strokes and Piece Editor changes. A drawing that passes through another piece's shape, a template's or a level piece's, changes nothing but the drawn block.
  - Once a block has used it (`LevelNamedPiece.WasPlaced`), it is listed only while a block of the open level uses it: erasing its last block with a freehand right click, the Eraser, a right click, Delete or the tile's × deletes it from the list, and an undo that brings a block back brings the tile back (user request of 2026-09-26). The session keeps the record, so nothing else is lost; a piece drawn only in the Piece Editor keeps its tile.
  - A level piece never keeps the window dirty: only template footprints can wait for the piece library (DEC-180). Nothing is restored when a level opens: the section reads the level's blocks and `pieces` table, so tiles, names and the Pen's level-piece edit come back after a closed window or an Editor restart.
- **Freehand drawing (rule 1).** User decisions of 2026-09-25: freehand drawing starts from the "+" tile, not from a Pen with nothing armed, and there is no separate pencil tile. A Pen with nothing armed keeps the "Pick a piece in Blocks" hint.
  - The "+" tile raises `PieceCreateRequested`, which makes the named piece and arms the Pen in freehand mode (`LevelEditorToolState.ArmFreehand`, `IsFreehandArmed`). It clears any armed piece and the Barrier brush, and gets the armed white outline. The Pen badge shows as usual.
  - Click-to-grow (user feedback of 2026-09-25: single clicks, not only press-and-drag). A left press starts a stroke on a free cell or on the piece's own block; a release without moving is a one-cell click. `LevelCanvasWalk.AddCrossedCells` walks cell by cell to the pointer, so a fast drag leaves no gap. Each free cell joins the stroke once. Another block, a board object (any level cell object, `LevelCanvasModel.IsBoardObject`), a void or an off-board cell is crossed but skipped. A press on another block or a board object starts nothing. The general place and move rule is unchanged.
  - The canvas knows the piece's drawn block (`SetFreehandBlock`, by id). With no stroke, the hovered cell shows a green ghost when a click would add it (`CanGrowPieceAt`: free, inside the piece limits and, once the piece has a block, edge-adjacent to it), and a red one otherwise. ### Template delete (DEC-126, 2026-09-26, `TASK-20260926-191802848-515eb50b-level-editor-template-delete-choices`; choices revised by DEC-193)

User request and answers of 2026-09-26: deleting a template (a library piece) that blocks of the active level database use asks what happens to those blocks, from both delete buttons. For template deletes in the active database this supersedes D2-A and AC-9 of `TASK-20260925-082521498-8e54a900` ("a deleted library piece only warns"); a library change made in the Piece Editor that keeps the piece still keeps D2-A and the manual Re-stamp. Since DEC-193 the choices are Delete template, Delete template and its blocks, and Cancel; Make Custom, its `Custom_` ids and the reserved identities are gone.

- **When.** A template no block uses, counted by key in the open draft and the saved levels, keeps the two-button delete and texts (`ConfirmPieceDelete`); so does any template while the level JSON cannot be read. With a Level Editor open, the pending template refusal (DEC-125) runs first, from the tile × and from the Piece Editor route alike. Without a Level Editor window no pending template edit can exist, because those edits live only in an open window's draft and piece session, so the window-less path has nothing to refuse.
- **Plan.** `LevelPieceDeletePlan` (plain C#, `Editor/Levels/Canvas`) only reads. It counts the blocks per level (the blocks whose cells form the template's key), the open level marked, and computes both options for every saved record and the draft:
  - **Delete template** keeps the blocks: their cells, colour, origin and effects stay, and so does their key, which is a level piece once the template is gone. Each level that uses them names that key after the template in its `pieces` table (`LevelPieceNames.SetName`), so they keep the template's name. There is no relabel and no reserved identity. It is impossible only when a written record fails `LevelData.Validate`.
  - **Delete template and its blocks** removes the blocks back to front (`LevelEditCommands.TryRemoveBlock`). A level whose written record keeps no block is deleted, and the question lists it under "These levels will be deleted because no block would remain:", adding "<Level> has unsaved changes, which will be lost." for a dirty open level. It is impossible when the database would keep no level ("Level database has no levels.") or a written record fails `LevelData.Validate`, for example an effect naming a removed block.
  - Only written records are validated; the open draft may become empty, and Save Level then reports it.
- **Question.** `ChoosePieceDelete` (default `DisplayDialogComplex("Delete Piece", message, "Delete template", "Cancel", "Delete template and its blocks")`: Enter picks Delete template, Esc and the close box Cancel). With one possible option it has two buttons; with none, no dialog opens and the status names both reasons. The message starts "Delete {name} from the piece library? N block(s) in M level(s) keep their cells as level pieces and take the name {name}.", then lists the per-level counts, what each option does, the levels the second option would delete, and each other level database's count as unchanged (`CountOtherDatabaseUses`, read only).
- **Order.** Before the question: Play Mode, the library record, and for the project library writable files and the piece JSON current on disk (`LevelPieceDeleteRoute.GetLibraryIssue`). After it: one atomic database write through `WriteLevels` (default `SaveLevels`, whose backup keeps the pre-delete JSON for Restore Previous Save); then the draft change as one undo step ("Name Template Blocks" or "Delete Piece Blocks") with the saved baseline (`m_savedDraftJson`) moved by the same change, so a clean draft stays clean and unsaved edits keep their undo history, or, when Delete template and its blocks deleted the open level, the nearest remaining level opens as after Delete Level; then the undoable `ShapeLibraryAuthoring.Delete` (`DeletePieceFromLibrary` seam, by key); then the catalog, palette, tool and level-choice refresh and a status naming the kept or removed blocks and the deleted levels. A failed write changes nothing. A write that `SaveLevels` completed but could not reload stops the delete there: the status says the level JSON was written, the piece and the draft are unchanged, and Reload JSON followed by another delete finishes it. A failed library delete keeps the written levels, which are valid, and the status says to press × again, which then takes the two-button path. The first Ctrl+Z restores the piece in the library, the second the draft's blocks; the written levels stay.
- **Session.** Nothing is renamed when a commit drops a template: a tracked level piece keeps its token and cells, and its key is simply no template's any more.
- **Piece Editor.** "Delete selected piece" of the active piece database first calls `PieceEditorWindow.DeleteLibraryPiece`, a plain `Func<ShapeKey, string>` that the `[InitializeOnLoad]` `LevelPieceDeleteRoute` sets, so BoardKit names no Level Editor type. With a Level Editor open, its draft-aware flow runs (`LevelDatabaseWindow.DeleteLibraryPiece`). ### Validate Level (DEC-144, 2026-09-28, `TASK-20260927-220047618-95397edf-level-editor-validate-level`)

User order of 2026-09-28; the case brief's optional "Level validation" item and a first slice of PRD 7.9 (REQ-O2). The editor tells the designer whether the open level can be solved without boosters, and Save Level warns before it writes a level that is proven unsolvable or could not be confirmed.

- **Button.** `validate-level` ("Validate Level") sits between Save Level and Test Level, built with `CreateBottomButton` (30 px high, at least 120 px wide, 13 px text): at bottom-bar index 1 until DEC-170, in the validation panel's button row since. Tooltip: "Check whether this level can be solved without boosters." It is enabled exactly when Save Level is (valid source, a level open, no error in Issues) and the Editor is not playing or entering Play Mode. Blocked tooltips: "Fix the errors in Issues first, …" and "Validate Level is unavailable in Play Mode. …". A click shows the result sentence in the status line and, since DEC-170, the answer and its listed solutions in the validation panel: it never saves and never changes the draft, its Undo history or the dirty marker.
- **Pipeline.** One plain C# check, `LevelSolvabilityCheck.Run`, serves the button and Save Level. It lives in the Editor-only `ColorBlockJam.Editor.Validation` assembly (`Editor/Levels/Validation/`, references `ColorBlockJam.Domain` and `ColorBlockJam.Runtime` only; `ColorBlockJam.Editor` references it, no runtime assembly does).
  1. Stage 1 is the existing structural validation: the button is disabled while Issues holds an error, and Save Level refuses as before.
  2. Support gate: a block, gate or board-object effect without solver support gives Not checked without a search, because the check never calls a level "Solvable" under rules it ignores (DEC-MECH-12). Support is a table keyed by effect type id in the Validation assembly (`LevelSolverSupport`); `arrow` and `ice` are supported today (Arrow since DEC-158). More than 16 blocks also gives Not checked.
  3. Stage 2 pre-checks, each "Cannot be solved" with a named reason and no search. PRE-1: a block has no gate of its colour (the message names the narrowest gate it could use, its smaller extent), needs a wider one (the message names the width), or cannot reach one it fits through on an otherwise empty board. PRE-2: an Ice block's count is greater than the number of other blocks. PRE-3 (DEC-176): a group of blocks is wedged, that is, with every other block taken away none of them has a slide or an exit from its authored origin (the largest such group, found as a fixpoint over the cached tables with Arrow axes applied and Ice ignored); it never moves, so the check stops before the search and names the group.
  4. Stage 3 is a breadth-first search over one-cell slides and exits in a fixed order (block index ascending; +X, -X, +Y, -Y; then exit sides), bounded by 1,000,000 stored positions and 15 s since DEC-175 (250,000 and 3.0 s under DEC-144; `LevelCheckOptions`, the only place the constants live; no override UI yet). Only an exhausted search is "Cannot be solved"; a budget hit is always "Not confirmed".
  - The rules are not re-implemented (AR-10). `LevelSolverModelBuilder` turns `LevelData` into a Domain `LevelModel` (a parity test pins it to `AttemptLevelConverter`). `LevelSolverTables` asks `MoveRules.CanOccupy` and `ExitRules.Evaluate` once per block and origin on a one-block board and caches the answers as cell masks (the footprint per origin and, for each fitting exit, the cells that must be empty, found by probing the Domain predicate). The search combines masks and never branches on an effect type; Ice is one hook (a frozen block cannot move or exit while `clearsToThaw` minus the exited blocks is above 0), and Arrow another (`LevelSolverMoves`: an Arrow block slides only along its axis and exits only through a side that axis points to, as `ArrowAxisConstraint` and `ArrowExitGate` rule the game; a block without Arrow has both axes, and blocks never split). The state key is each on-board block's origin cell plus one exited bit per block (at most 128 bits). Exits only free cells and lower Ice counts, so an available exit is taken eagerly; a test proves eager and plain breadth-first search agree.
- **Texts** (status line; colour, shape and cell, never ids or type names):
  - The shape is the piece's name from `LevelValidationFlow.ShapeNames`: before each check the window reads the templates' names and the level's piece names on the main thread into one lookup (`LevelPieceEditController.CreateShapeNameLookup`, DEC-193), which a background check calls on its worker thread (DEC-175). A piece without a name reads "{n}-cell".
  - `Solvable in N moves.` (`1 move.` for one). N counts player moves: consecutive steps of one block merge into one move (DEC-122). The search is shortest in one-cell steps, not necessarily in moves.
  - `Cannot be solved: {reason}.`, for example "the Red Single block at (0,0) has no Red gate; it needs one at least 1 cell wide", "the Red Single block at (0,1) and the Orange Single block at (1,1) are wedged against each other and can never move" (PRE-3), or after an exhausted search "the Red Single block at (1,0) and the Orange Single block at (1,2) can never leave" (DEC-176). The exhausted search records every block that left in some stored position and names the others, at most three by name and the rest counted ("and 2 other blocks"). That is a proof: moves are reversible and an exit only frees cells and thaws Ice, so a block that can leave in some reachable position can also leave after every other block that can. Before DEC-176 an exhausted search read `no sequence of moves clears every block`, which stays only as an unreachable fallback.
  - A `Not confirmed` answer names no block: under a budget hit, a block that has not left yet may simply leave late in a solution.
  - `Not confirmed: the check stopped after 1,000,000 positions.` or `… after 15 seconds.` (250,000 and 3 before DEC-175)

The start board shows 0.4 s, a one-cell step 0.25 s, an exit 0.4 s and the last, cleared board 1.0 s (`k_startSeconds`, `k_stepSeconds`, `k_exitSeconds`, `k_clearedSeconds`, the only place the pace lives; Revision 1 slowed the first 0.1, 0.1, 0.2 and 0.6 s); then the draft shows again. A late update skips to the frame whose time has come.
  - Controls (Revision 1): **Pause** keeps the shown frame and removes the update callback, so nothing ticks while paused; **Resume** shows the next frame after the shown frame's full time; **Step** pauses a playing solution first and shows exactly one more frame, and a Step on the last frame, the cleared board, ends the playback like its time would (the draft comes back); **Stop** ends it. The state and timing live in `LevelSolutionPlayback` (`Pause`, `Resume`, `Step`, `Stop`, `IsActive`, `IsPaused`, `IsPlaying`; `Play(..., paused)` for Auto Play off); the panel only shows it (`SetPlayback`) and forwards clicks (`PauseResumeClicked`, `StepClicked`, `StopClicked`). The controls sit inside the row button, so their container stops every pointer, mouse, click and submit event before it reaches the row: a control click never counts as a row click.
  - Arrow keys (Revision 2, amended for the safety order): while a solution shows and the Level Editor has the keyboard focus outside a text field, → shows the next frame (`LevelSolutionPlayback.StepForward`: pauses first; on the cleared board it only pauses and never ends the playback, so a held → stops there instead of running on into nudging a block) and ← shows the previous frame (`StepBack`: pauses first, and on the start board does nothing, playing or paused). Neither subscribes the update callback. The Step control keeps ending the playback on the cleared board (`Step` uses `StepForward` and ends only there). Only the keys that would otherwise nudge a block count (no Ctrl, Cmd or Alt; `StepSolutionByKey` in the root key handler, before any shortcut). Both are consumed (`StopImmediatePropagation`, `PreventDefault`), so they neither nudge a block nor run another shortcut, and they never stop or end the playback. With no solution shown they keep their old meaning. The control tooltips name the keys, for example "Pause the solution on this frame. ← and → step through the frames." and "Show the next frame; on the last frame this button shows the level again. → and ← show the next and the previous frame and stay on the solution.". Frames reach the canvas through `SetModel`, never `SyncCanvas`, so the stored selection is not resolved against a frame; the selection outline and a Pen edit's green outline and cells hide while it plays (`SetSelection`, `SetFreehandBlock`), also through a tool change meanwhile, and come back after as the window's state has them. No playback starts in Play Mode.
  - Preview frames: each frame is also raised through `LevelDatabaseWindow.SolutionFramePublished`, an editor-only static event apart from `DraftLevelPublished` (DEC-102). A frame never becomes `LastPublishedLevel`; after the end or a stop the window publishes its draft on the next editor update. While the LevelEditor scene is loaded, the scene preview shows the same frames, the cleared board included ([Level Editor Scene Preview](Level-Editor-Scene-Preview.md#solution-playback-frames)).
  - Stop points, for a playing or a paused solution alike: the active row's Stop button (Revision 1; until then a second click on the playing row); another row, which replaces it with that entry's start board (the only stop that shows no draft in between); a press on the canvas, which only stops (`StopImmediatePropagation` and `PreventDefault` keep it from every canvas tool, so it edits nothing); any draft change, undo or redo; a level or JSON switch; Save Level, Validate Level or Test Level; `ExitingEditMode`; the window's `OnDisable`, which publishes the draft at once, and so a domain reload. Each stop unsubscribes the update callback at once (a paused playback has none) and shows the draft (after a switch, the new level) with its selection and the ▶ glyphs.
  - Safety stop (Revision 2): while a solution shows, any pointer press or key press in the window outside `validation-panel` stops it before it does anything else. The root's `TrickleDown` `PointerDownEvent` handler (`OnWindowPointerDown`, which also forgets an unfinished canvas press) and its key handler (`OnKeyDown`, after the ← and → step keys) run first, one of each per GUI build. Neither consumes the event: a tools-column button, a colour swatch, a tile, a top-bar field or dropdown, the issues list, the splitter or the bottom bar, a shortcut, Delete, Ctrl+Z or typing then does its normal work on the restored draft. ## 3. Canvas rendering

`LevelCanvasElement : VisualElement` (`Editor/Levels/Canvas/`), one element, one `generateVisualContent` pass with `Painter2D` (rectangles as four `LineTo`; ring corners as arcs). No child element per cell.

- **Sizing** (`LevelCanvasGeometry`): on `GeometryChangedEvent`, `cell = floor(min((w - 2m) / (W + 1), (h - 2m) / (H + 1)))`, the +1 reserving the half-cell ring per side; `cell >= 18`; board centred; row `H-1` drawn at the top (PRD coordinates).
- **Layers, back to front:** floor (`PaletteColor.Ground`; a void cell stays unpainted, like the space outside the walls, and grid lines skip it), rule-set wall glyphs (`PaletteColor.Wall`; see Gates, edges, walls and issues), doors (bars per segment in the door colour, 0.5 cell outward, as deep as the wall ring they open (user feedback of 2026-09-25), with a small direction notch), blocks (cell union in the block colour, 2 px outline on edges not shared within the block), ghost (green/red, 50 %), hatch (resize preview: red diagonals), selection (3 px white outline), grid lines (1 px, 0.35 grey), effect overlays: Arrow badges (see below), issue highlight (3 px red outline).
- **Labels:** one child `Label` per block, `text = block.Id` (plain string, no formatting; ZString is not referenced by `ColorBlockJam.Editor.asmdef` and is not needed), `PickingMode.Ignore`, positioned in `SetModel` and on geometry change only.
  - The canvas shows the id upper case; the level data keeps it as authored. The label is centred on the footprint's centre when the half-cell area around that point lies on the block (a shared edge or corner counts), else on the block cell nearest it, so a 7 shape's label stays off the block beside it (D-001, 2026-09-26), in a 2 x 1 cell box with a font of 0.4 cell (11-20 px).
  - Every label has a dark 1 px text outline (`unityTextOutlineWidth`/`unityTextOutlineColor`), so the id reads over an Arrow badge and on every block colour (`TASK-20260926-212320271-98b25efa-level-editor-arrow-markers`, revision 1).
- **Arrow badge** (catalog BLK-01, same task, revision 1, user request of 2026-09-27 "tam ortadan çıkmalı"): a block with a valid Arrow effect gets a white double-headed arrow with a dark outline, in the same `generateVisualContent` pass (painter calls only, no allocation, no pointer input). The badges are an effect overlay above the grid lines, so the grid line on an even-width block's centre line does not run through the white shaft. Since `TASK-20260926-230921278-a3ffdc40-arrow-block-gameplay` (DEC-158) `ArrowCanvasEffectLayer` draws them, with the same look, through the canvas's effect layer list (see [Block Effects Architecture](Block-Effects-Architecture.md) section 6): on each model it derives every block's `ArrowMarker` from the block's typed `ArrowEffect` and its cells with `ArrowMarkerRun` (`Runtime/Board`), the rule the scene preview and the Game scene share:
  - The arrow is centred on the footprint's bounding box on both axes, so a 2 x 2 block's arrow runs on the line between its columns (or rows). On an L or T footprint it stays on the box centre, even where that crosses an empty part of the box.
  - This overrides the catalog's BLK-01 view rule ("the run through the bounds center, ties to the lower index"), which put a 2 x 2 block's arrow on its left column. DEC-158 records it, and the catalog notes it.
  - Its length is the box's extent along the axis, clamped to 1-3 cells: the same Arrow_1-Arrow_3 the preview and the game show, never stretched. The tips are inset 0.14 cell from the ends.
  - An Effect Editor edit, its undo or an axis change builds a new model, so the badge follows at once. A block without a valid Arrow effect has none.
  - The Arrow drag and exit constraint (BLK-01 gameplay) is implemented in the Game scene (DEC-158); the badge stays presentation only. The scene preview attaches its markers through `ArrowPreviewEffect`, which also rejects a level whose piece catalog lacks an `Arrow_N` prefab before the preview changes.
  - Tests: `ArrowMarkerRunTests`, `CanvasArrowBadgeTests` (a repaint draws one badge per Arrow block, read through `ArrowCanvasEffectLayer.DrawnBadgeCount` via `LevelCanvasElement.GetEffectLayer<ArrowCanvasEffectLayer>()`).
- **Cheapness:** the element holds an immutable `LevelCanvasModel`. `MarkDirtyRepaint()` runs only on `SetModel`, hover change, selection change, tool change, geometry change. Hover change is decided by plain C# `LevelCanvasHover.Update(CanvasHit) -> bool changed` (compared by cell/segment, not pixels), which is what the test asserts; no counter on `MarkDirtyRepaint`. No `schedule` loops. Palette colours cached once per `SetPalette`.
- **Input:** `PointerDown/Move/Up/CaptureOut` on the element, `CapturePointer` during drags, translated by `LevelCanvasHitTest` into `CanvasHit { Kind: Cell | RingSegment | Block | Door | Outside; Cell; Side; Index; EntityId }`. Corners are `Outside`.

## 4. Data flow

```
bound fields ──SerializedProperty──┐
                                   ▼
canvas gesture ─► LevelEditCommands (pure: LevelData in → LevelData out | issue)
                    └─► Undo.RegisterCompleteObjectUndo(m_draft, label); LevelDraft.Replace(level)
                                   │
        TrackSerializedObjectValue(m_draftObject) ─► OnDraftChanged()
                                   │
   hasUnsavedChanges • RefreshBlockTools • LevelDraftIssues → issues list • canvas.SetModel • SchedulePublish()
                                                                       └─► DraftLevelPublished → Scene preview
```

- `LevelDraft` is the **single undo target and source of truth**. Add `internal void Replace(LevelData)`. Both the canvas commands and the bound fields record undo on the same object, so Ctrl+Z is one history.
- Change tracking moves from `SerializedPropertyChangeEvent` on `m_draftFields` (`:165`) to `TrackSerializedObjectValue(m_draftObject, OnDraftChanged)` (present in 2022.3 `UnityEditor.UIElements.BindingExtensions`), which also catches array add/remove in the Raw data foldouts.
- `OnEnable`: `Undo.undoRedoPerformed += OnUndoRedo`; `OnDisable` removes it. `OnUndoRedo`: if `LevelDatabaseAddressables` active GUID differs from the loaded one (the `TrySetActive` undo record at `LevelDatabaseAddressables.cs:203`), re-run the database selection refresh; else `m_draftObject.Update()` + `OnDraftChanged()`.
- Every gesture is one undo group (`IncrementCurrentGroup` at pointer down, `SetCurrentGroupName`, increment at pointer up; pattern `PieceEditorWindow.cs:442-471`). `DestroyDraft` calls `Undo.ClearUndo(m_draft)` before `DestroyImmediate`.
- **Save keeps history:** after a successful Save of the same level ID, the draft is not rebuilt; only `m_savedDraftJson` and `hasUnsavedChanges` reset. Reload, Restore, level switch and database switch rebuild the draft and clear its undo (stated in the status line). Open decision 3.
- Commands never construct records from scratch except when creating one; edits go through one `LevelRecordCopy` helper (`Editor/Levels/Canvas/`) that copies every field of `LevelBlockData` / `LevelDoorData` and changes only the edited ones. Since level JSON v2 landed, the helper also carries void cells, block and door effects and cell objects, so no command drops them (task B defect D-005, `LevelEditV2FieldsTests`). A resize shifts void cells and cell objects with the content, except a void on the resized side's outermost line, which follows that edge instead (a cut corner stays a corner) unless its new cell cannot be void; a cell object in a removed line is removed whole and reported as a board object. Joining two gates is refused when the absorbed gate has effects.
- Save Level, Refresh, Restore, `+`, `×`, Create/Delete Database, `AskToLeaveDraft`, stale-file check, backups and the duplicate-ID check are untouched. Draft edits never touch disk.
- The `"red"` starter-colour bug (`LevelDatabaseWindow.cs:677,681`) is **not** bundled here; it is filed through `task-bug` against the task that wrote `CreateLevel`.

### Level databases as folders (DEC-196, 2026-09-29)

A level database is the folder `Data/Json/Levels/<Name>/` with `manifest.json` and pack files of about 100 levels ([Level Data Format](Level-Data-Format.md#level-databases-manifest-and-packs-dec-196)). The window still holds every level of the database in its own catalog, so every cross-level feature (duplicate IDs, template re-stamps and deletes, piece names) is unchanged.

- **Dropdown.** It lists the manifests of the Level Database group by database name (the folder). Pack files never show. The shipped database is `Main`; it cannot be deleted.
- **Create Database.** `+` names a new folder; it gets a manifest with no pack, and its first Create Level opens `pack-001.json`.
- **Delete Database.** `×` deletes the whole folder and its group entries after one confirmation, and `Main` becomes the active game database.
- **Saves.** `LevelSaveController` keeps a `LevelDatabaseSnapshot` (every file's text) instead of one JSON text. Save Level, Create Level, Delete Level, Restore Previous Save, the template delete (both routes) and the CBJ import save through `LevelDatabaseAssets`: the external-change check covers every file of the database, the backup is the whole database in `Library/ColorBlockJam/LevelBackups/<manifest GUID>/`, only the packs whose text changes are written, then the manifest when its text changes, then unlisted packs are deleted through `AssetDatabase.DeleteAsset`, then the files are imported and `LevelDatabaseAddressables.TrySync` registers them. A save that changes no text keeps the backup. Status texts name the database (`Saved Level 3 to Main.`).
- **Reload keys.** The draft's reload copy and the other-level caches key on the snapshot's content hash instead of the JSON text.
- **Migration.** `Color Block Jam/Data/Split Level JSON into Packs` turns a single-file level JSON into a database folder, keeping its GUID on the manifest.
